# Chess Engine Core Repair Spec

## Purpose

This document defines the required repair pass for the chess engine after the code review of the uploaded `chess-engine-master` repository.

The current implementation is not trustworthy as a chess engine. The primary failures are not cosmetic. The code has a contradictory board-coordinate convention, regular piece movement is not actually validated, legal move generation returns moves for both sides, clone/simulation state diverges, check/checkmate/stalemate APIs are broken, and CI is not running the pytest suite correctly.

This spec is the authoritative implementation contract for the repair pass. If older docs, comments, tests, or code disagree with this spec, this spec wins.

## Current observed baseline

From a clean checkout of the uploaded repository:

```bash
python -m pytest tests -q
```

Observed result:

```text
97 tests collected
76 passed
21 failed
```

Representative failures and defects:

- `parse_move_notation("e2e4")` resolves to a square containing a black pawn in the starting position.
- `parse_move_notation("e7e5")` resolves to a square containing a white pawn in the starting position.
- Rooks, bishops, queens, knights, kings, and pawns can pass invalid geometry checks because `MoveValidator.is_valid_move()` does not require the destination to be generated by piece-specific movement rules.
- `Board.get_legal_moves()` returns legal moves for both colors instead of only the side to move.
- `Board.is_in_check()`, `Board.is_checkmate()`, and `Board.is_stalemate()` delegate to missing `BoardState` methods.
- `main.py` calls `board.is_checkmate()` and `board.is_stalemate()` without the required color argument.
- `Board.clone()` copies `Board.board` but does not reconnect `Board._board_state.board`, validators, and executors to the cloned board.
- En passant contains contradictory logic and comments, including treating an en passant capture as a two-rank diagonal jump.
- Castling rights are not reliably cleared after king/rook movement or rook capture.
- Debug `print()` calls remain in engine code.
- GitHub Actions uses `requirements.txt` and `unittest`, but this repo has no `requirements.txt` and uses pytest tests.

## Non-negotiable goals

1. The engine must use one canonical coordinate system everywhere.
2. Algebraic notation such as `e2e4` must work from the standard starting position.
3. `make_move()` must reject all illegal piece movement geometry.
4. `get_legal_moves()` must return only legal moves for the side to move unless explicitly asked for a square.
5. The engine must correctly detect check, checkmate, and stalemate.
6. Castling, en passant, and promotion must follow standard chess rules.
7. Cloned boards must be safe for AI/search simulation.
8. CI must actually run the pytest suite.
9. Existing tests may be corrected if they encode the old broken coordinate convention, but tests must not be weakened to hide bugs.

## Canonical coordinate system

Use the standard array representation already stated in `THE_PLAN.md` and `README.md`:

```text
Internal board indexes:
  row 0 = rank 8
  row 1 = rank 7
  row 2 = rank 6
  row 3 = rank 5
  row 4 = rank 4
  row 5 = rank 3
  row 6 = rank 2
  row 7 = rank 1

  col 0 = file a
  col 1 = file b
  col 2 = file c
  col 3 = file d
  col 4 = file e
  col 5 = file f
  col 6 = file g
  col 7 = file h
```

Therefore:

```text
a8 = row 0, col 0
e8 = row 0, col 4
h8 = row 0, col 7

a7 = row 1, col 0
e7 = row 1, col 4
h7 = row 1, col 7

a2 = row 6, col 0
e2 = row 6, col 4
h2 = row 6, col 7

a1 = row 7, col 0
e1 = row 7, col 4
h1 = row 7, col 7
```

Algebraic conversion must be:

```python
row = 8 - rank
col = ord(file_char) - ord("a")
rank = 8 - row
file_char = chr(ord("a") + col)
```

### Row constants

The existing `ROW_1`, `ROW_2`, ..., `ROW_8` names are currently misleading because `ROW_1` has value `0`. That is incompatible with the canonical coordinate system.

Implement one of these two approaches. Prefer Option A.

### Option A: rank-semantic row constants, preferred

Define the rank-named row constants by their real internal row index:

```python
ROW_8 = RowConstant(0)
ROW_7 = RowConstant(1)
ROW_6 = RowConstant(2)
ROW_5 = RowConstant(3)
ROW_4 = RowConstant(4)
ROW_3 = RowConstant(5)
ROW_2 = RowConstant(6)
ROW_1 = RowConstant(7)
```

Then:

```python
ConstantSquare(row=ROW_1, col=COL_E) == e1
ConstantSquare(row=ROW_2, col=COL_E) == e2
ConstantSquare(row=ROW_7, col=COL_E) == e7
ConstantSquare(row=ROW_8, col=COL_E) == e8
```

`get_row_constant(index)` must return the row constant for an internal row index:

```python
get_row_constant(0) is ROW_8
get_row_constant(1) is ROW_7
get_row_constant(2) is ROW_6
get_row_constant(3) is ROW_5
get_row_constant(4) is ROW_4
get_row_constant(5) is ROW_3
get_row_constant(6) is ROW_2
get_row_constant(7) is ROW_1
```

`RowConstant.__repr__()` should show rank-semantic names, not `self._value + 1`. For example, `repr(ROW_8)` should be `ROW_8`, and `repr(ROW_1)` should be `ROW_1`.

### Option B: remove rank-named row constants

Remove or de-emphasize `ROW_1`...`ROW_8` and use internal row indexes directly through `get_row_constant(index)`. This is less invasive in concept but will require more test and doc churn. Only choose this if Option A becomes too messy.

## Starting board layout

The standard initial position must be:

```text
row 0 / rank 8: black rook, knight, bishop, queen, king, bishop, knight, rook
row 1 / rank 7: black pawns
row 2 / rank 6: empty
row 3 / rank 5: empty
row 4 / rank 4: empty
row 5 / rank 3: empty
row 6 / rank 2: white pawns
row 7 / rank 1: white rook, knight, bishop, queen, king, bishop, knight, rook
```

Required smoke checks:

```python
assert board.get_piece(algebraic_to_index("e2")).color == Color.WHITE
assert board.get_piece(algebraic_to_index("e2")).kind == PieceType.PAWN
assert board.get_piece(algebraic_to_index("e7")).color == Color.BLACK
assert board.get_piece(algebraic_to_index("e7")).kind == PieceType.PAWN
assert board.get_piece(algebraic_to_index("e1")).kind == PieceType.KING
assert board.get_piece(algebraic_to_index("e8")).kind == PieceType.KING
```

## Pawn movement rules

Under the canonical coordinate system:

```text
White moves toward decreasing row indexes.
Black moves toward increasing row indexes.
```

Therefore:

```python
white_forward_delta = -1
black_forward_delta = +1
white_start_row = 6  # rank 2
black_start_row = 1  # rank 7
white_promotion_row = 0  # rank 8
black_promotion_row = 7  # rank 1
```

Required legal examples from the starting position:

```text
e2e3 legal
e2e4 legal
e7e6 legal
e7e5 legal
```

Required illegal examples from the starting position:

```text
e2e5 illegal
e2d3 illegal unless a black piece is on d3 or d3 is the en passant target
e2e1 illegal
```

## Move-generation and validation architecture

The engine must have a strict separation between pseudo-legal moves and legal moves.

### BoardState

`BoardState` should be a state container with simple accessors. It may provide `get_piece`, `set_piece`, `clear_square`, `find_king`, and `clone`, but it should not contain high-level chess policy unless intentionally redesigned.

Required state:

```python
board: list[list[Piece | None]]
turn: Color
en_passant_target: ConstantSquare | None
white_kingside: bool
white_queenside: bool
black_kingside: bool
black_queenside: bool
```

All engine components must reference the same `BoardState` object or the same underlying board data. Do not allow `Board.board` and `Board._board_state.board` to diverge.

### Pseudo-legal move generation

`PieceMovers.get_valid_moves(piece, board_state)` should return pseudo-legal destination squares for the given piece based on:

- piece movement geometry,
- board occupancy,
- sliding-piece path blocking,
- pawn forward/capture rules,
- pawn two-square start move,
- normal captures,
- optionally special move candidates if the architecture explicitly supports them.

Pseudo-legal generation does not need to check whether the moving side's own king is left in check. That filtering belongs to legal move validation.

### Legal move validation

`MoveValidator.is_valid_move(from_square, to_square)` must perform this flow:

1. Source square must contain a piece.
2. The moving piece color must be the side to move when called through `Board.make_move()`.
3. Destination must not contain a friendly piece.
4. If the move is castling, validate castling through the castling validator.
5. If the move is en passant, validate en passant through the en passant validator.
6. Otherwise, the destination square must appear in the moving piece's pseudo-legal moves.
7. Simulate the move on a cloned state.
8. Reject the move if the moving side's own king is in check after the move.
9. Accept the move only after all checks pass.

Regular moves must not be accepted merely because the destination is empty or occupied by an enemy piece. The piece-specific geometry check is mandatory.

### Public piece-specific validators

The public methods below must call the same legal validation path and must therefore reject illegal geometry and blocked paths:

```python
Board.is_valid_rook_move(...)
Board.is_valid_bishop_move(...)
Board.is_valid_queen_move(...)
Board.is_valid_knight_move(...)
Board.is_valid_king_move(...)
Board.is_valid_pawn_move(...)
```

These methods should additionally verify that the source square contains the expected piece type.

## Legal move generation

`Board.get_legal_moves(square: ConstantSquare | None = None)` must behave as follows:

- If `square` is provided:
  - Return legal moves only for the piece on that square.
  - If the square is empty, return an empty list.
  - If the piece on that square is not the side to move, return an empty list unless the public API explicitly documents otherwise.
- If `square` is not provided:
  - Return legal moves only for `Board.turn`.
  - Do not include moves for the opponent.

Returned moves should preserve the existing tuple shape unless the project is deliberately migrated to the existing `LegalMove` dataclass:

```python
list[tuple[ConstantSquare, ConstantSquare, PieceType | None]]
```

Promotion moves should include promotion information when needed. At minimum, queen promotion must work. Prefer generating all legal promotion choices: queen, rook, bishop, knight.

## Check, checkmate, and stalemate

Implement check detection in one canonical place. Acceptable choices:

- `MoveValidator.is_in_check(color)`
- `Board.is_in_check(color)` with helper functions
- a dedicated `CheckDetector`

Do not call missing methods on `BoardState`.

Required behavior:

```python
Board.is_in_check(color: Color) -> bool
Board.is_checkmate(color: Color | None = None) -> bool
Board.is_stalemate(color: Color | None = None) -> bool
```

If `color` is `None`, use `self.turn`.

Definitions:

```text
in check: the king of color is attacked by at least one enemy piece.
checkmate: color is in check and has zero legal moves.
stalemate: color is not in check and has zero legal moves.
```

Attack detection must not accidentally use full legal move validation in a way that recurses infinitely. For attack detection:

- Pawns attack diagonally forward only, not their forward move squares.
- Knights attack L-shaped squares.
- Bishops attack diagonals with clear path.
- Rooks attack ranks/files with clear path.
- Queens attack rook + bishop lines with clear path.
- Kings attack adjacent squares.

## Castling rules

Castling must follow standard chess rules:

- King and relevant rook must be present on their original squares.
- The relevant castling right must still be true.
- Squares between king and rook must be empty.
- The king must not currently be in check.
- The king must not pass through an attacked square.
- The king must not land on an attacked square.
- Castling cannot capture a piece.

Canonical squares:

```text
White kingside:  e1 -> g1, rook h1 -> f1
White queenside: e1 -> c1, rook a1 -> d1
Black kingside:  e8 -> g8, rook h8 -> f8
Black queenside: e8 -> c8, rook a8 -> d8
```

Castling rights must be cleared:

- White king moves: clear white kingside and white queenside.
- Black king moves: clear black kingside and black queenside.
- White rook moves from h1: clear white kingside.
- White rook moves from a1: clear white queenside.
- Black rook moves from h8: clear black kingside.
- Black rook moves from a8: clear black queenside.
- A rook is captured on h1: clear white kingside.
- A rook is captured on a1: clear white queenside.
- A rook is captured on h8: clear black kingside.
- A rook is captured on a8: clear black queenside.

## En passant rules

En passant must follow standard chess rules.

After a pawn moves two squares, set `en_passant_target` to the square it passed over.

Examples:

```text
White e2e4 sets en_passant_target = e3.
Black d7d5 sets en_passant_target = d6.
```

An en passant capture is legal only on the immediately following half-move.

White example:

```text
White pawn on e5.
Black plays d7d5, setting en_passant_target to d6.
White may play e5d6.
The white pawn lands on d6.
The black pawn on d5 is removed.
```

Black example:

```text
Black pawn on d4.
White plays e2e4, setting en_passant_target to e3.
Black may play d4e3.
The black pawn lands on e3.
The white pawn on e4 is removed.
```

En passant capture geometry is one row forward and one file sideways, not a two-row diagonal jump.

Under the canonical coordinate system:

```python
# For white en passant capture
row_delta = -1
col_delta = +/-1
captured_pawn_square = ConstantSquare(row=from_square.row, col=to_square.col)

# For black en passant capture
row_delta = +1
col_delta = +/-1
captured_pawn_square = ConstantSquare(row=from_square.row, col=to_square.col)
```

Clear `en_passant_target` after every move unless the current move was a two-square pawn advance that creates a new target.

## Promotion rules

Promotion must occur when a pawn reaches the last rank:

```text
White promotion row: row 0 / rank 8
Black promotion row: row 7 / rank 1
```

Accepted promotion pieces:

```text
queen, rook, bishop, knight
```

Illegal promotion pieces:

```text
king, pawn, empty/none if explicit invalid choice is provided
```

If the move reaches a promotion square and no promotion piece is provided, default to queen unless the existing CLI/API contract intentionally requires explicit promotion.

CLI notation must support:

```text
e7e8q
e7e8r
e7e8b
e7e8n
```

with the correct canonical mapping.

## Move execution

`MoveExecutor.execute_move()` must assume the move has already been validated and then update the board atomically.

For every executed move:

1. Capture any destination piece if present.
2. Update castling rights based on the moving piece and captured piece.
3. Move the piece.
4. Handle special move side effects:
   - castling rook move,
   - en passant captured pawn removal,
   - promotion replacement.
5. Update the moved piece's `_square`.
6. Clear the source square.
7. Update en passant target.
8. Flip the side to move exactly once.

Avoid duplicated turn/en-passant updates between `Board.make_move()` and `MoveExecutor`. There should be one canonical place for each state transition.

## Clone/simulation requirements

Cloning must be safe for AI and king-safety simulation.

Required behavior:

```python
clone = board.clone()
assert clone is not board
assert clone._board_state is not board._board_state
assert clone._board_state.board is clone.board
assert clone.board is not board.board
```

Pieces in the clone should be independent `Piece` objects. Moving a piece on the clone must not mutate the original piece's `_square`.

All validators/executors inside the clone must reference the clone's `BoardState`, not the original board's state.

## AI requirements for this repair pass

Do not expand the AI feature set during this repair pass. First make the rules engine correct.

Minimum AI-related repairs:

- AI must only consume legal moves for the current side to move.
- AI board simulation must use a correct clone.
- Any transposition key/FEN-like key must include at least:
  - board placement,
  - side to move,
  - castling rights,
  - en passant target.

The CLI currently accepts `--ai`, but `_game_loop()` ignores `use_ai` and `ai_depth`. Either wire this correctly or remove/disable the option with a clear message. Do not leave a fake AI flag that has no effect.

## CLI requirements

The CLI must support normal coordinate notation:

```text
e2e4
e7e5
g1f3
b8c6
e7e8q
```

`_game_over_message()` must call checkmate/stalemate APIs correctly. Acceptable pattern:

```python
if board.is_checkmate(board.turn): ...
if board.is_stalemate(board.turn): ...
```

or, if the default argument is implemented:

```python
if board.is_checkmate(): ...
if board.is_stalemate(): ...
```

The CLI must not crash after a legal move because of missing color arguments or missing `BoardState` methods.

## Tests

The test suite must be updated to encode the canonical coordinate system. Do not preserve tests that accidentally assert the old broken mapping.

Add or fix tests for:

- Algebraic coordinate conversion.
- Initial board placement.
- Standard opening moves from algebraic notation.
- Illegal sliding-piece blocked paths.
- Illegal piece geometry for rook, bishop, queen, knight, king, and pawn.
- Legal move generation only for side to move.
- Clone independence.
- Check detection.
- Checkmate detection.
- Stalemate detection.
- Castling rights updates after king move, rook move, and rook capture.
- En passant target creation, expiration, white capture, black capture, and captured-pawn removal.
- Promotion for all four legal promotion pieces.
- CLI parsing and game-over call path.

Before changing tests, classify each failing test as one of:

```text
A. Test is correct and implementation is wrong.
B. Test encodes old/broken coordinate convention and must be rewritten.
C. Test is ambiguous and needs to be rewritten to use algebraic helpers.
```

Prefer tests that use algebraic square helpers for readability:

```python
sq("e2")
sq("e4")
```

rather than raw row constants unless the test is specifically about internals.

## CI and packaging

Fix `.github/workflows/ci.yml` so it actually runs this repo's tests.

Minimum acceptable workflow:

```yaml
- name: Install package and test dependencies
  run: |
    python -m pip install --upgrade pip
    python -m pip install -e .
    python -m pip install pytest pydantic

- name: Run tests
  run: python -m pytest tests -q
```

If dependencies are formalized in `pyproject.toml`, prefer that over ad-hoc installs.

`python -m unittest discover -s tests` is not acceptable because it does not run the pytest suite correctly.

## Acceptance criteria

The repair pass is complete only when all of the following are true:

```bash
python -m pytest tests -q
```

passes with zero failures.

Additional required smoke checks:

```python
from chess_game.chess.board import Board
from chess_game.chess.move import parse_move_notation
from chess_game.chess.types import Color, PieceType
from chess_game.chess.coords import algebraic_to_index, index_to_algebraic

board = Board()

assert index_to_algebraic(algebraic_to_index("a1")) == "a1"
assert index_to_algebraic(algebraic_to_index("e2")) == "e2"
assert index_to_algebraic(algebraic_to_index("e7")) == "e7"
assert index_to_algebraic(algebraic_to_index("h8")) == "h8"

assert board.get_piece(algebraic_to_index("e2")).color == Color.WHITE
assert board.get_piece(algebraic_to_index("e2")).kind == PieceType.PAWN
assert board.get_piece(algebraic_to_index("e7")).color == Color.BLACK
assert board.get_piece(algebraic_to_index("e7")).kind == PieceType.PAWN

move = parse_move_notation("e2e4")
assert board.make_move(move.start, move.end, move.promotion) is True
assert board.get_piece(algebraic_to_index("e4")).color == Color.WHITE
assert board.turn == Color.BLACK

move = parse_move_notation("e7e5")
assert board.make_move(move.start, move.end, move.promotion) is True
assert board.get_piece(algebraic_to_index("e5")).color == Color.BLACK
assert board.turn == Color.WHITE
```

Also required:

- A rook cannot move diagonally.
- A bishop cannot move straight.
- A queen cannot move like a knight.
- A knight cannot move straight or diagonally.
- A king cannot move two squares except valid castling.
- A pawn cannot move backward.
- A pawn cannot capture forward.
- A sliding piece cannot move through any intervening piece.
- `Board.get_legal_moves()` on the initial position returns only White legal moves and does not include Black moves.
- `Board.clone()` can be mutated without changing the original board.
- The CLI does not crash after a legal move.
- GitHub Actions runs pytest.
